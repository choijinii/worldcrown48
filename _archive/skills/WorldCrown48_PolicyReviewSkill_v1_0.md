# WorldCrown48 — 정책 검토 및 설계 결정 스킬 v1.0

## 이 스킬의 목적

설계서 검토 세션에서 반복적으로 나타난 **의사결정 패턴**과 **정책 원칙**을 기록합니다.
다음 버전 업 작업 시 동일한 실수를 반복하지 않기 위한 체크리스트입니다.

---

## PART 1 — 투표 정책 결정 원칙

### 1-1. 랜덤 매치 관련 규정 금지 원칙

```
❌ 절대 금지: "같은 Match 하루 N회 금지" 류의 규정
이유:
  - 랜덤 매치 알고리즘에서 동일 Match 재출현은 필연적 (하루 최대 4회)
  - 기술적으로 막을 수 없음 → 규정 자체가 무의미
  - 정상 투표를 방해하는 UX 역효과 발생

✅ 올바른 규정 구조:
  - 대진별 1일 5회 (tournament 단위 카운트)
  - 자정(KST 00:00) 리셋
  - Match 단위 제한 없음
```

**검증 질문:** 새로운 투표 제한 규정을 추가할 때 반드시 확인
> "이 규정이 랜덤 매치 환경에서 자연스럽게 발생하는 상황을 막지는 않는가?"

---

### 1-2. 부정투표 방어 MVP 단계 원칙

```
부정투표 방어 시스템은 실데이터를 보고 나서 설계해야 효과적이다.

MVP 1: Rate Limiting만 (봇 자동 차단 최소선)
MVP 2: fingerprintjs 디바이스 핑거프린트
MVP 3: 완전한 3단계 차단 시스템 (실데이터 기반 설계)

결정 기준:
  - "이 기능이 없으면 MVP 런칭이 불가능한가?" → YES면 MVP 1
  - "실데이터 없이도 설계할 수 있는가?" → NO면 MVP 3
  - "중간 복잡도이며 K-POP 팬덤 유입 시 필요한가?" → MVP 2
```

---

### 1-3. 부정투표 UX 원칙

```
❌ 금지: 부정투표 팝업 표시
이유:
  - 정상 유저 UX 방해
  - 서비스 신뢰도 하락
  - 법적 효력 없음

✅ 올바른 방향:
  - Policy Hub 이용약관에 "투표 공정성 및 부정 행위 금지" 조항 신설
  - 약관 동의 = 법적 효력 발생
  - Rate Limiting이 봇 자동 차단 (팝업 불필요)

약관 조항 필수 포함 내용:
  1. 다중 계정 투표 금지
  2. 자동화 스크립트·봇·매크로 금지
  3. VPN·프록시 IP 우회 금지
  4. 타인 계정 이용 금지
  5. 위반 시 계정 정지/영구 차단/법적 조치 고지
  6. 부정 투표 결과 무효 처리 권한 명시
```

## PART 2 — 뉴스 생성 설계 원칙

### 2-1. 뉴스 트리거 이원화 원칙

```
뉴스 생성 트리거는 두 가지여야 한다:

트리거 1: 크라운 결정 이벤트 (먼저 구현)
  - Round Deadline 마감 → Match 승자 확정 = 뉴스 발생
  - 장점: 정형 포맷, 구현 쉬움, 매 라운드 보장 발생
  - Cloud Functions: onRoundDeadlineReached → generateCrownNews()

트리거 2: 특이점 탐지 (이후 구현)
  - 지지율 급변·지역 편차 임계값 초과 감지
  - 장점: 흥미로운 스토리 뉴스 생성 가능
  - 단점: 구현 복잡도 높음, 임계값 튜닝 필요

구현 순서: 크라운 결정 이벤트 → 특이점 탐지
이유: 크라운 이벤트가 더 간단하고 뉴스 공급이 보장됨
```

**검증 질문:** 뉴스 생성 로직 설계 시
> "크라운(라운드 결과)이 결정되는 것 자체가 뉴스가 되는가?" → YES면 이벤트 트리거 먼저

## PART 3 — 도메인 명칭 충돌 방지 원칙

### 3-1. 명칭 충돌 체크리스트

새 모듈/페이지 명칭 결정 시 반드시 아래 확인:

```
확인 체크리스트:
  □ 기존 5+1개 도메인(Pitch/Lab/Arena/LockerRoom/PolicyHub/AdminDashboard)과 유사하지 않은가?
  □ 관리자 영역(Domain 6)의 명칭이 유저 영역(Domain 1~5)과 혼동되지 않는가?
  □ 같은 개념을 다른 도메인에서 다른 이름으로 부르지 않는가?

대표 사례 (v4.5 수정):
  - "대진 상세페이지" (Domain 6 M4) → "대진 운영 현황"으로 변경
    이유: Domain 3(The Arena)에도 대진 상세 화면이 존재해 혼동 발생
    
명칭 구분 원칙:
  - 관리자 영역: "운영", "관리", "처리", "현황" 등의 단어 사용
  - 유저 영역: "투표", "결과", "랭킹", "공유" 등의 단어 사용
```

## PART 4 — 반응형 전략 결정 원칙

### 4-1. 도메인별 반응형 우선순위

```
반응형 결정 기준:
  "이 도메인의 주 사용자는 누구인가?"
  "해당 사용자의 주 기기는 무엇인가?"

MVP 1 모바일+데스크탑 필수:
  - Domain 1 (The Pitch): 유저 첫 접점, 모바일 60%+
  - Domain 3 (The Arena): 핵심 투표 화면, 스마트폰이 주 투표 기기

데스크탑 전용 (관리자/약관):
  - Domain 2 (The Lab): 관리자 전용, 이미지 업로드 = PC 작업
  - Domain 5 (Policy Hub): 약관 텍스트, 모바일 최적화 불필요
  - Domain 6 (Admin Dashboard): 관리자 전용

MVP 2부터 모바일 대응:
  - Domain 4 (Locker Room): MVP 2 오픈 시 모바일 포함

구현 팁:
  Tailwind CSS 반응형 유틸 (sm:, md:, lg: 접두사)을
  처음부터 쓰면 나중에 추가하는 것보다 공수가 훨씬 적음.
  Domain 1, 3은 처음부터 반응형으로 작성할 것.
```

## PART 5 — 설계서 버전 업 체크리스트

설계서 새 버전을 작성하기 전 아래 항목을 반드시 점검:

```
투표 정책 관련:
  □ "같은 Match 하루 N회" 류의 규정이 있는가? → 있으면 삭제
  □ 부정투표 팝업 표시 항목이 있는가? → 있으면 삭제, 약관 조항으로 대체
  □ 랜덤 매치 불가능 가정을 한 규칙이 있는가? → 있으면 삭제

뉴스 관련:
  □ 뉴스 생성 트리거가 특이점 탐지만인가? → 크라운 결정 이벤트 추가 필요
  □ 크라운 결정 이벤트 트리거가 특이점보다 먼저 구현으로 되어 있는가?

명칭 관련:
  □ 관리자 도메인(Domain 6)의 모듈명이 유저 도메인과 중복되는가?
  □ "AI 채유기" 오타가 있는가? → "AI 채우기"로 수정

반응형 관련:
  □ 에이전트 임무에 Domain 1, 3 모바일 반응형이 명시되어 있는가?
  □ Domain 6 에이전트에 데스크탑 전용이 명시되어 있는가?

MVP 범위 관련:
  □ 부정투표 3단계 차단 시스템이 MVP 1~2에 포함되어 있는가? → MVP 3으로 이연
  □ fingerprintjs가 MVP 1에 포함되어 있는가? → MVP 2로 이연
  □ Rate Limiting(봇 방어)이 MVP 1에 있는가? → 반드시 MVP 1 유지
```
