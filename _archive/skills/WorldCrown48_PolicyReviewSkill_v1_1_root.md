## PART 1 — 투표 정책 결정 원칙

### 1-1. 랜덤 매치 관련 규정 금지 원칙

```
❌ 절대 금지: "같은 Match 하루 N회 금지" 류의 규정
이유:
  - 랜덤 매치 알고리즘에서 동일 Match 재출현은 필연적 (하루 최대 4회)
  - 기술적으로 막을 수 없음 → 규정 자체가 무의미
  - 정상 투표를 방해하는 UX 역효과 발생

✅ 올바른 규정 구조 (CONTEXT.md v0.5 기준):
  - 대진별 1일 5회 (tournament 단위 카운트)
  - 자정(KST 00:00) 리셋
  - Match 단위 제한 없음
```

**검증 질문:** 새로운 투표 제한 규정을 추가할 때 반드시 확인
> "이 규정이 랜덤 매치 환경에서 자연스럽게 발생하는 상황을 막지는 않는가?"

---

### 1-2. 부정투표 방어 MVP 단계 원칙

```
MVP 1: Rate Limiting만 (1분 10회+ → 15분 쿨다운) + 소셜 로그인 필수
MVP 2: fingerprintjs 디바이스 핑거프린트 + IP 중복 방지
MVP 3: 완전한 3단계 차단 시스템 (실데이터 기반 설계)

결정 기준:
  - "이 기능이 없으면 MVP 런칭이 불가능한가?" → YES면 MVP 1
  - "실데이터 없이도 설계할 수 있는가?" → NO면 MVP 3
  - "중간 복잡도이며 K-POP 팬덤 유입 시 필요한가?" → MVP 2
```

---

### 1-3. 부정투표 UX 원칙

```
❌ 금지: 부정투표 팝업 표시 (정상 유저 UX 방해, 서비스 신뢰도 하락)

✅ 올바른 방향:
  - Policy Hub 이용약관에 "투표 공정성 및 부정 행위 금지" 조항 신설
  - 약관 동의 = 법적 효력 발생
  - Rate Limiting이 봇 자동 차단 (팝업 불필요)

약관 조항 필수 포함:
  1. 다중 계정 투표 금지
  2. 자동화 스크립트·봇·매크로 금지
  3. VPN·프록시 IP 우회 금지
  4. 타인 계정 이용 금지
  5. 위반 시 계정 정지/영구 차단/법적 조치 고지
  6. 부정 투표 결과 무효 처리 권한 명시
```

## PART 2 — 뉴스 생성 설계 원칙

### 2-1. 뉴스 트리거 이원화 원칙 (★ v1.1 교정)

```
뉴스 생성 트리거는 두 가지여야 한다:

트리거 1: Champion 확정 이벤트 (먼저 구현)  ← ★ v1.1 교정
  - Voter가 결승 Match 완료 → Champion 확정 = 뉴스 발생
  - 장점: 정형 포맷, 구현 쉬움, 결승마다 보장 발생
  - Cloud Functions: onChampionConfirmed → generateCrownNews()  ← ★ 올바른 함수명

트리거 2: 특이점 탐지 (이후 구현)
  - 지지율 급변·지역 편차 임계값 초과 감지
  - Cloud Functions: onVoteAnomalyDetected → generateTrendNews()
  - 단점: 구현 복잡도 높음, 임계값 튜닝 필요

구현 순서: Champion 확정 이벤트 → 특이점 탐지

❌ 삭제된 잘못된 표현 (v1.0):
  "Round Deadline 마감 → Match 승자 확정 = 뉴스 발생"  ← Round Deadline 없음!
  "onRoundDeadlineReached → generateCrownNews()"       ← 금지 개념 함수명!
```

> ⚠️ **핵심 원칙**: Round에는 Deadline이 없다.
> 라운드 전환은 Voter의 마지막 Match 완료 → advanceRound() 시스템 자동 실행.
> 뉴스 생성 트리거는 시간 기반이 아닌 **이벤트 기반(Champion 확정, 이상 감지)**이다.

**검증 질문:** 뉴스 생성 로직 설계 시
> "Champion(왕관)이 결정되는 것 자체가 뉴스가 되는가?" → YES면 이벤트 트리거 먼저

## PART 3 — 도메인 명칭 충돌 방지 원칙

### 3-1. 명칭 충돌 체크리스트

새 모듈/페이지 명칭 결정 시 반드시 아래 확인:

```
확인 체크리스트:
  □ 기존 7개 도메인(D0~D6)과 유사하지 않은가?  ← ★ v1.1: 5+1 → 7개로 업데이트
  □ 관리자 영역(Domain 6)의 명칭이 유저 영역(Domain 1~5)과 혼동되지 않는가?
  □ 같은 개념을 다른 도메인에서 다른 이름으로 부르지 않는가?

명칭 구분 원칙:
  - 관리자 영역: "운영", "관리", "처리", "현황" 등의 단어 사용
  - 유저 영역: "투표", "결과", "랭킹", "공유" 등의 단어 사용

대표 사례 (v4.5 수정):
  "대진 상세페이지" (Domain 6 M4) → "대진 운영 현황"으로 변경
  이유: Domain 3(The Arena)에도 대진 상세 화면이 존재해 혼동 발생
```

## PART 5 — 설계서 버전 업 체크리스트 (★ v1.1 v4.8 기준 갱신)

설계서 새 버전을 작성하기 전 아래 항목을 반드시 점검:

```
[ 투표 정책 관련 ]
  □ "같은 Match 하루 N회" 류의 규정이 있는가? → 있으면 삭제
  □ 부정투표 팝업 표시 항목이 있는가? → 있으면 삭제, 약관 조항으로 대체
  □ "1일 1회" 투표 제한이 있는가? → "1일 5회"로 교정 (CONTEXT.md v0.5 기준)
  □ 랜덤 매치 불가능 가정을 한 규칙이 있는가? → 있으면 삭제

[ Round/Deadline 관련 — ★ v1.1 신규 ]
  □ "Round Deadline" 단어가 어디든 있는가? → 즉시 삭제. 존재하지 않는 개념.
  □ "라운드 마감일", "라운드 기간" 표현이 있는가? → 즉시 삭제
  □ "onRoundDeadlineReached()" 함수명이 있는가? → onChampionConfirmed()로 교체
  □ "Host가 다음 라운드를 시작한다" 표현이 있는가? → 삭제. 시스템 자동.
  □ rounds[].deadline 필드가 스키마에 있는가? → 즉시 삭제
  □ Tournament Deadline과 Round Deadline을 혼용하고 있는가? → Tournament만 존재

[ 뉴스 관련 ]
  □ 뉴스 생성 트리거가 특이점 탐지만인가? → Champion 확정 이벤트 추가 필요
  □ "Round Deadline 마감" → 뉴스 트리거로 쓰고 있는가? → Champion 확정으로 교체
  □ Champion 확정 이벤트 트리거가 특이점보다 먼저 구현으로 되어 있는가?

[ 명칭 관련 ]
  □ "Candidate"가 남아있는가? → "Contestant"로 교체
  □ "Battle"이 남아있는가? → "Match"로 교체
  □ 관리자 도메인(Domain 6)의 모듈명이 유저 도메인과 중복되는가?

[ 반응형 관련 — ★ v1.1 교정 ]

  □ Domain 2, 6 에이전트에 데스크탑 전용이 명시되어 있는가?
```
