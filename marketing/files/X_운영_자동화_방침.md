## 1. 왜 런칭 전에는 자동화하지 않는가

### 1-1. 신규 계정 정지 위험

계정을 만들자마자 API로 자동 게시를 시작하면 자동화 계정으로 분류될 위험이 있습니다.
정확한 판정 기준은 X가 공개하지 않으므로 **저는 모릅니다.** 다만 구조적으로 이렇습니다.

- 우리 계정은 런칭 마케팅의 **단일 창구**입니다. 대체 채널이 없습니다.
- 정지되면 복구에 며칠이 걸리고, 복구된다는 보장도 없습니다.
- 런칭 3일 총공 기간에 정지되면 그 자리에서 캠페인이 끝납니다.

D-38 시점에 얻는 편의보다 잃을 수 있는 것이 훨씬 큽니다.

### 1-2. 자동화로 얻는 게 별로 없다

런칭 전 게시 빈도는 하루 1~3건입니다. 사람이 붙여 넣는 데 5분입니다.
자동화 구현·인증·디버깅에 드는 시간이 절약되는 시간보다 큽니다.

### 1-3. 초기 계정은 사람 손이 필요하다

팔로우, 답글, 인용, 커뮤니티 반응 — 초반 계정 성장은 대화에서 나옵니다.
자동 게시로는 안 됩니다.

## 3. Cowork이 지금 만들 것 — 게시물 큐

### 3-1. 파일

`marketing/10_content/x_queue.md` 를 만듭니다.

### 3-2. 항목 형식

각 게시물은 아래 항목을 갖습니다.

- **발행 예정일** — 날짜만. 시각은 대표님이 판단
- **분류** — 소개 / 카운트다운 / 토너먼트 예고 / 데이터 / 기사 연동 / 답례
- **본문(KO)** — 한국어
- **본문(EN)** — 영어
- **첨부** — 이미지 파일명 또는 없음
- **링크** — UTM 포함 완성형 URL
- **상태** — 대기 / 발행완료

### 3-3. 링크 규칙

큐에 들어가는 링크는 **UTM이 붙은 완성형**이어야 합니다.
UTM_RULES v1.0 §2 규칙을 따릅니다. 우리 계정이 올리는 게시물이므로 매체는 `social`입니다.

- `utm_source` = `x`
- `utm_medium` = `social`  ← 유저 공유(`share`)와 구분되어야 함. 섞이면 계측이 무의미해집니다
- `utm_campaign` = 해당 대회 슬러그 또는 `prelaunch`
- `utm_content` = 게시물 성격 (`og_card` / `news_article` / `profile_link`)

### 3-4. 큐 채우기 우선순위

1. 고정 게시물 1건
2. 사전등록 안내 3건 (문구 변형)
3. 토너먼트 4종 예고 각 1건
4. 카운트다운 (D-30 / D-14 / D-7 / D-3 / D-1)

본문 초안은 마케팅 채팅에서 제공합니다. Cowork은 **구조와 파일**을 만들어 주십시오.

## 4. 런칭 후 — 여기서부터 자동화

런칭 후 자동화의 값은 게시 편의가 아니라 **우리 정체성 구현**에 있습니다.

목표는 '인용되는 출처'입니다. 그러려면 랭킹 변동이 **꾸준하고 기계적으로** 나가야 합니다.
사람이 매일 쓰면 빠지는 날이 생기고, 빠지는 순간 참조할 수 없는 출처가 됩니다.

### 4-1. 자동 게시 후보

| 유형 | 주기 | 내용 |
|---|---|---|
| 일일 랭킹 | 매일 1회 | 4종 대회 1~3위 변동 |
| 순위 역전 | 발생 시 | 1위가 바뀐 순간 |
| 마일스톤 | 도달 시 | 누적 투표 수 단위 돌파 |

### 4-2. 전제 조건

- 계정이 **최소 2~3주 정상 운영**된 뒤에 붙일 것
- 모든 자동 게시는 **우리 데이터만** 사용. 외부 사실 인용 금지 (팩트 슬롯 규칙 적용 대상 아님)
- 발행 전 사람이 볼 수 있도록 **초안 상태로 큐에 쌓고, 발행은 승인 후**

### 4-3. 구현 시점

런칭 후 2주차부터 검토. **지금은 착수하지 않습니다.**
현재 개발 우선순위는 아레나 개편 · 런칭 전 게이트 · 사전등록 UTM 유지입니다.
