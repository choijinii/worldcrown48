## §1 필독 컨텍스트 (인라인 — 외부 메모리 참조 없음)

**있는 것(재사용)**: `lib/embed/`(LAB-EV-1) = 검증 함수(videos.list, embeddable·지역·연령, 50개/1콜) + 3층 추천(댓글 타임스탬프→챕터→첫 후렴) + LoopPlayer + 검수기 모달(`YouTubeInspectorModal`, onApply로 슬롯 주입 경로 존재) + 주간 재검증 크론. YouTube 키는 Secret `YOUTUBE_API_KEY`(서버 전용). AI 콜러블은 `requireAdmin` + `ai_usage/{date}` 일일 캡 패턴(AI-1) — 같은 패턴을 따를 것. 편집기 카드 하단의 `imageSearchKeyword`(예 "BLACKPINK Jisoo stage performance")가 AI가 이미 남긴 **검색어 힌트**다.

**설계 결정(대표 확정 2026-08-16)**: ① 파이프라인은 사이트 안(Lab 편집기 UI + 서버 함수), 별도 프로그램 아님. ② E단계(운영자 승인·생성 클릭)는 사람. ③ 캐시 = 검색어별 후보 목록 저장·TTL 7일·수동 갱신 버튼·중복 회피(단일 영상 고정 금지 — 신선도·다양성 이유). ④ 풀은 항상 48(대진 흐름 #10), 브래킷 크기는 Voter 선택 — 소싱은 48명 전부. ⑤ 유튜브 검색이 사실상 **실존 검증** 역할(AI-1 후속 D-1).

**YouTube 할당량 사실**: 무료, 프로젝트당 하루 10,000유닛(태평양 자정 리셋). `search.list` = **100유닛/회**, `videos.list` = 1유닛/50개. 48명 풀 소싱 = 최대 4,800유닛(캐시 적중 시 감소) → 하루 2개 토너먼트가 무료 한도. 증설은 무료·심사(운영자 단계 불필요 — §9).

**용어**: 슬롯 = 편집기 카드 1칸. media.embed = LAB-EV-1이 확장한 저장 필드(W6, 카드가 읽는 곳).

## §2 규모 실측
신규: 서버 함수 1~2개(콜러블, 배치형), 캐시·쿼터 컬렉션 2개, UI 버튼+진행률+슬롯 상태, 테스트. 수정: TournamentCreator(버튼·주입 연결), lib/embed(재사용 확장 소폭). 실측 다르면 보고하되 계속.

## §3 스코프
**IN**: 검색(search.list, `type=video&videoEmbeddable=true&videoSyndicated=true&maxResults=15`) · 캐시·TTL·중복 회피 · 할당량 가드 · 검증(재사용) · 관련성 판정(규칙→Haiku 폴백) · 재시도 루프(최대 3후보) · 진행률 UI · 슬롯 상태 · [새 영상 찾기] · 실존 의심 표시 · 스모크 실측.
**OUT**: 저가 검색 API 백업 경로(설계 훅만 남김: `SearchProvider` 인터페이스로 YouTube 구현 1개) · 참가자 DB 축적 · MVP2 유저 공개(requireAdmin 유지) · 표시 용어/3언어(v2.0 별도) · 토너먼트 자동 생성 · 검색어 AI 재작성(힌트 있으면 그대로, 없을 때만 "이름 + 카테고리 키워드" 조합).

## §4 RULE
- R1 키 서버 전용, 클라이언트에서 YouTube 직접 호출 금지. 로그에 키 금지.
- R2 48 리터럴 금지 — TOTAL_CONTESTANTS(단일 소스)에서 파생.
- R3 LAB-EV-1 코어 함수 재사용, 복제 금지. 새 로직은 `lib/embed/sourcing/`에.
- R4 **할당량 가드는 실행 전에** — 필요 유닛(미적중 후보 수 × 100 + 검증 콜) 계산 → 잔여 미만이면 거부. 카운터는 트랜잭션.
- R5 배치 실행: 콜러블 1회 = 최대 8명(60s 타임아웃 안전) — 클라이언트가 순차 호출하며 진행률 표시. 부분 실패는 슬롯 단위로 격리.
- R6 E단계 사람 — 결과는 슬롯에 "제안" 상태로 주입, 운영자가 훑고 [토너먼트 생성]. 자동 발행 금지.
- R7 hex guard·시각 토큰 준수, 화면은 기존 검수기 모달의 시각 언어 재사용.
- R8 추측 금지: search.list 파라미터·유닛 비용은 Google 문서 실측 후 사용.

## §5 Phase
- **A** 코어(lib/embed/sourcing): SearchProvider(YouTube) · 캐시(get/put, TTL, 후보 목록) · 쿼터 카운터 · 관련성 판정(규칙: 이름/그룹/영문명 토큰 매칭, 채널 allow-hint "official/Mnet/KBS/SBS/MBC/M2/1theK" 가점 → 미달 시 Haiku 배치 판정) · 파이프라인 `sourceOne(contestant, ctx)`(검색→후보 순회→검증(재사용)→관련성→추천 구간→결과) — 모의 API 단위 테스트(캐시 적중/미적중, 쿼터 거부, 3회 실패, 중복 회피, 0건→실존 의심).
- **B** 콜러블 `autoSourceVideos`(requireAdmin, 배치 ≤8, 입력: 토너먼트 초안의 후보 슬라이스, 출력: 슬롯별 결과) + `refreshSlotVideo`(캐시 우회 1명). AI-1 패턴의 일일 캡 재사용(호출 횟수 캡, 예 20/일).
- **C** UI: STEP 2 채우기 바에 `[🔍 영상 자동 소싱]` → 확인 다이얼로그(예상 유닛·잔여 표시) → 진행률 → 슬롯 상태 배지(제안/수동 필요·사유/실존 의심) → 슬롯 `[새 영상 찾기]` → 기존 onApply 경로로 media.embed 주입. 콘솔 오류 0.
- **D** PR 4블록 → CI → 프리뷰 SHA 확인(프리뷰는 옛 functions를 치므로 UI 렌더만) → 머지 → functions 배포(main 전용).
- **E** 대표 스모크(프로덕션): ① 후보 6명 드라이런 → 결과·유닛 확인 ② 48명 풀 실행 → 표(성공 n/수동 m/실존 의심 k/캐시 적중률/유닛/시간) ③ 같은 토너먼트 재실행 → 캐시 적중으로 유닛 ≈0 확인 ④ 슬롯 1개 [새 영상 찾기].

## §6 Auto-STOP
- 기존 onApply/미디어 주입 경로가 배치 주입에 부적합(시그니처·상태 관리) → STOP.
- search.list의 embeddable 필터가 문서와 다르게 동작하거나 유닛 비용 문서 확인 불가 → STOP.
- 관련성 규칙만으로 판정 불가 비율이 30% 초과(Haiku 비용·시간 급증) → STOP 후 보고.
- 60s 타임아웃 내 8명 처리 불가(실측) → 배치 크기 조정안과 함께 STOP.
- 쿼터 카운터가 실제 Google 사용량과 크게 어긋남(스모크에서 확인) → STOP.
- 대진 흐름·검수기 ADR과 충돌 발견 → STOP.
