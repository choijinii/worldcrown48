# 킥 프로세스 플레이북 v1.0
### "킥 발행 → Claude Code 실행 → Auto-STOP 협의 → 검증 → 배포" 생산 라인을 다른 프로젝트·다른 개발자에게 이식하기 위한 전체 패키지

작성 2026-08-16 · WorldCrown48에서 TOK-1(211건 hex 토큰 스윕)과 LAB-EV-1(유튜브 임베드 검수기) 두 킥으로 실증된 프로세스를 일반화한 문서. 코딩 초보인 1인 기획자가 AI 에이전트 둘(설계 파트너 + 실행 파트너)과 함께 프로덕션 배포까지 완주하는 방식.

---

## 0. 한 장 요약

이 프로세스의 본질은 **"실행 AI에게 자유를 주되, 멈춰야 할 지점을 문서로 미리 정해두는 것"**이다. 킥(Kick) 문서가 그 계약서다. 사람은 코드를 쓰지 않는다. 사람은 세 가지만 한다 — 결정, 눈으로 검증, 그리고 자기 계정이 필요한 일(API 키, 로그인, 결제).

```
[대표 + Cowork]  설계 토의 → 킥 문서 발행 → outputs/handoffs-staging/ 에 저장
        ↓
[Claude Code]     킥 읽고 착수 → Phase별 실행 → 규칙 위반·판단 필요 지점에서 Auto-STOP
        ↓
[대표 ⇄ Cowork]   STOP 화면 캡처 → Cowork가 읽고 선택지 해설 → 대표 결정 → 붙여넣기
        ↓
[Claude Code]     PR 생성 → CI(테스트+가드) → 프리뷰 배포
        ↓
[대표]            프리뷰/프로덕션에서 눈으로 검증(시각·스모크) → 머지 승인
        ↓
[Claude Code]     머지 → 배포 → 최종 보고(4블록 + "핸드오프와 달랐던 점") → 워크트리 정리
        ↓
[Cowork]          메모리 갱신 · 교훈 기록 · 다음 킥 대기열 정리
```

두 킥의 실측: TOK-1 약 4시간(Auto-STOP 3회), LAB-EV-1 약 5시간(Auto-STOP 2회). 사람이 키보드 앞에 있어야 했던 시간은 각각 30분 미만.

## 1. 세 역할과 경계

| 역할 | 맡는 것 | 맡지 않는 것 |
|---|---|---|
| **대표(사람)** | 최종 결정, 눈으로 하는 검증(디자인·UX·콘텐츠), 자기 계정이 필요한 작업(API 키 발급·Secrets 등록·로그인이 필요한 화면 테스트·결제), 우선순위 | 코드 작성, 명령어 암기, 로그 해석 |
| **설계 파트너(Cowork)** | 아이디어 토의, 구조·흐름 시각화, 킥 문서 작성, Auto-STOP 화면 해설과 선택지 추천, 프로젝트 메모리 유지, 교훈 기록 | 리포에 직접 커밋(리포 밖에서 산다), 실행 AI의 대변인 노릇(실측이 우선) |
| **실행 파트너(Claude Code)** | 킥 읽고 구현, 테스트·가드·CI, PR·머지·배포, 실측 보고, 킥과 다른 판단이 필요하면 STOP | 킥에 없는 스코프 확장, 추측을 사실처럼 보고, 사람 확인 없이 프로덕션 시각 변경 |

경계에서 배운 것 하나. **설계 파트너의 메모리와 실행 파트너의 메모리는 서로 보이지 않는다.** 킥 문서에 "Cowork 메모리 X 참조"라고 쓰면 실행 파트너는 그 파일을 찾을 수 없다. 필요한 내용은 킥 본문에 인라인으로 넣는다(TOK-1·LAB-EV-1 둘 다 이 실수를 했고, 둘 다 실행 파트너가 정직하게 "없다"고 보고해서 문제가 안 됐을 뿐이다).

## 2. 킥 문서 템플릿 (필수 섹션)

킥 문서는 계약서다. 아래 섹션이 빠지면 실행 AI가 스스로 채우게 되고, 그 지점에서 스코프가 새거나 추측이 들어간다.

| § | 섹션 | 무엇을 쓰나 | 왜 필요한가 |
|---|---|---|---|
| 0 | **한 줄 목적 + 완료 정의(DoD)** | "무엇이 어떻게 되면 끝인가"를 체크리스트로 | 실행 AI가 "다 됐다"를 스스로 판정할 기준 |
| 1 | **필독 컨텍스트(인라인)** | 관련 결정·규칙·용어를 본문에 직접 | 메모리 참조는 안 보임 |
| 2 | **규모 실측치** | 사전에 잡은 숫자(파일 수·건수)와 "실측이 다르면 보고하되 계속" | 추정과 실측이 다를 때 멈출지 갈지 미리 정함 |
| 3 | **스코프 IN / OUT** | 이번에 하는 것 · 절대 안 하는 것 · 후속 킥으로 넘기는 것 | 스코프 확장을 사전에 차단 |
| 4 | **RULE 목록** | 위반 불가 원칙(예: 시각 결과 불변, 추가만 허용, 48 하드코딩 금지, 키는 서버 전용) | 판단의 기준선 |
| 5 | **Phase 분할** | A→B→C… 각 Phase의 산출물과 커밋 단위 | 중간에 끊겨도(잠자기·API 오류) 이어받을 수 있음 |
| 6 | **Auto-STOP 조건** | "이 상황이면 반드시 멈추고 질문" 목록 | 프로세스의 심장. 아래 §4 참조 |
| 7 | **검증 하네스** | 기계 검증(테스트·가드·대조 스크립트)과 사람 검증(프리뷰 시각·스모크)의 분리 | "됐다"를 숫자로 증명 |
| 8 | **PR 본문 4블록** | A 변경 요약 · B 실측 수치 · C 검증 근거 · D 남긴 것/후속 (+E 사용자 영향 한 줄) | 나중에 읽는 사람을 위한 기록 |
| 9 | **대표 사전 준비물** | API 키·Secrets·계정 등 사람만 할 수 있는 것 | 착수 전 막힘 방지 |
| 10 | **"핸드오프와 달랐던 점" 보고 의무** | 킥 문면과 다르게 한 모든 것을 최종 보고에 기록 | 문서와 코드의 괴리를 잡는 장치 |
| 11 | **정리 절차** | 워크트리 제거, 브랜치 처리, 메모리 갱신 | 다음 킥이 깨끗한 바닥에서 시작 |

파일명 규약: `KICK_<코드>_<한글제목>_<YYYY-MM-DD>.md`, 위치 `outputs/handoffs-staging/`. 버전 수정 시 문서 상단에 v1.1 변경 요약 한 줄.

## 3. 리포 측 인프라 (한 번만 깔면 모든 킥이 재사용)

이 프로세스가 돌아가려면 리포 자체에 몇 가지 안전장치가 있어야 한다. WorldCrown48에는 이제 다 있고, 새 프로젝트에는 첫 킥(또는 "킥 0")으로 이걸 먼저 깐다.

**CLAUDE.md** — 실행 AI가 매 세션 읽는 프로젝트 헌법. 스택·규칙·금지사항. 핵심은 **실측 동기화**: 문서에 "Tailwind 사용"이라 써 있는데 실제로 없으면 실행 AI가 그 함정에 빠진다(TOK-1에서 실제로 발견·수정). "없는 것" 경고 블록을 두는 게 효과적이었다.

**가드 스크립트 + CI** — 규칙을 코드로 강제한다. 예: hex 색상 하드코딩 재유입 감시(`npm run check:hex`), 미사용 allowlist 항목 감지. 사람이 리뷰로 잡을 수 없는 것을 기계가 잡는다. 스캔 범위에서 `.claude/worktrees/` 등 도구 폴더는 제외할 것(오탐 159건 교훈).

**predeploy-guard** — 프로덕션 배포는 `main` 브랜치에서만 허용. 실행 AI가 아무리 자유로워도 브랜치에서 프로덕션을 건드릴 수 없게.

**Secrets** — API 키는 `firebase functions:secrets:set` 같은 서버 금고에만. 클라이언트 코드·리포·채팅에 절대 노출 금지. 새 키는 기존 키를 건드리지 않고 별도 생성 + 용도 제한.

**Worktree 관행** — 킥마다 `~/Projects/<repo>-<kick>` 워크트리에서 작업. 본 폴더는 항상 깨끗한 main. 끝나면 `git worktree remove`.

**테스트 기반선** — 유닛·룰·E2E가 이미 green인 상태. 킥은 여기에 "추가만" 한다. E2E가 "0건 실행 green"이 아닌지 로그로 확인하는 습관.

**PR 템플릿** — 위 4블록을 리포의 PR 템플릿으로 박아두면 실행 AI가 자동으로 채운다.

**handoffs-staging 폴더** — 킥 문서의 우편함. 실행 AI는 여기서 읽고, 완료 시 문서 하단에 완료 표시를 남긴다.

## 4. Auto-STOP 프로토콜 (프로세스의 심장)

실행 AI가 멈춰야 하는 조건을 킥마다 명시한다. 두 킥에서 실제로 발동한 유형은 다음과 같다.

| 유형 | 실제 사례 | 좋은 STOP의 조건 |
|---|---|---|
| **킥 문면과 실측이 충돌** | W6 저장 위치: 킥은 새 필드, 실제론 기존 저장소가 있어 이중장부 위험 | 근거(코드 위치)와 권장안을 함께 제시 |
| **RULE과 작업 충돌** | 폴백 hex 제거 시 실제 화면 색이 바뀜(시각 불변 위반) | 대안 2~3개와 (권장) 표시 |
| **스코프 경계 판단** | 핸드오프에 없는 파일 1건 발견 / .ts 8파일 포함 여부 | 포함·제외의 결과를 각각 설명 |
| **사람만 할 수 있는 일** | 실키 스모크(운영자 로그인 필요) / 403이면 IAM 의심 | 무엇을 어떻게 해달라는지 절차로 |
| **추측으로 채워야 하는 빈칸** | "차단 예상 링크 2개"를 못 찾음 → 추측 대신 대조군으로 대체하고 보고 | 추측하지 않았음을 명시 |

대표 측 응답 규약. STOP 화면을 캡처해 설계 파트너에게 보이면, 설계 파트너가 (권장) 옵션의 근거를 해설하고 붙여넣기용 답변을 만든다. 답변은 **번호로 대응 · 승인/거부 명시 · 조건 부가("근거를 남기고, 다르면 STOP") · "이후 Phase X 계속"**의 4요소. 지금까지 실행 AI의 (권장) 표시는 전부 정확했으므로, 급할 땐 (권장)을 따라도 안전했다.

주의: 실행 AI의 대화형 선택 UI에서 Esc를 누르면 "declined"로 닫히지만, 같은 내용을 일반 채팅으로 입력하면 그대로 이어진다. 막힌 게 아니다.

## 5. 검증 이중 구조

**기계 검증**은 실행 AI가 스스로 만든다 — 테스트, 가드, 그리고 필요하면 전용 하네스(TOK-1의 색상 대조 하네스: 9화면 1,836요소 계산 색상 전후 비교 → 실제 회귀 1건 검출·롤백). "화면이 안 바뀌었다"를 말이 아니라 숫자로.

**사람 검증**은 두 지점 — 프리뷰(머지 전, Vercel branch URL)와 프로덕션(머지 후). 프리뷰에서는 로그인이 안 되는 게 정상(Firebase 승인 도메인 미등록)이니, 로그인 뒤 화면은 프로덕션에서 30초 확인으로 대체한다. 실행 AI가 "여기를 중점으로 보라"고 지목한 지점(회귀가 났다가 롤백된 자리 등)을 우선 본다.

**스모크 테스트**는 실제 데이터로 실제 버튼을 누르는 것. 실행 AI가 준비물(링크·계정·기대값)을 표로 만들어 주면 대표가 실행하고 캡처로 보고. 기대값과 다르면 STOP.

## 6. 메모리·문서 동기화

세 곳에 기록이 산다. **설계 파트너 메모리**(프로젝트 결정·순서·미결·교훈), **실행 파트너 메모리**(리포 실측·기술 피드백), **리포 문서**(CLAUDE.md·규범 문서·킥). 셋은 자동으로 동기화되지 않는다. 규약:

킥이 끝날 때마다 설계 파트너가 메모리에 완료 상태·결정·교훈·다음 대기열을 갱신한다. 실행 AI의 "핸드오프와 달랐던 점"은 그대로 옮긴다. 결정이 바뀌었는데 규범 문서가 옛 원칙을 말하고 있으면(예: "창구 1원칙" 폐기 후) **Stale-Doc Guard 킥**을 따로 잡아 스윕한다 — 코드는 최신인데 문서가 옛날인 상태가 가장 위험하다.

## 7. 교훈 목록 (실제로 겪은 것만)

맥북 잠자기가 실행 AI 응답을 끊는다. 30분 넘는 작업은 `caffeinate -d`(터미널) 또는 잠자기 방지 설정. 작업물은 커밋되어 있으므로 "이어서 진행"이면 복구된다.

프리뷰 CI의 "fail"이 코드 실패가 아니라 "Vercel 프리뷰 URL 대기 시간 초과"인 경우가 있다. 로그를 읽고 재실행(`gh run rerun --failed`).

`firebase` 명령이 "Invalid project id"면 `--project <id>` 를 붙이거나 `firebase use --add`로 한 번 연결.

Secrets 입력 프롬프트는 붙여넣어도 화면에 아무것도 안 보인다. 한 번만 붙여넣고 Enter.

새 API 키는 새로 만든다. 자동 생성된 기존 키(Browser key 등)에 제한을 걸면 라이브 서비스가 멈춘다.

실행 AI가 스스로 저지른 실수(테스트 타입 오류)를 스스로 찾아 고치고 보고하는 건 신뢰의 신호다. 숨기지 않았다는 뜻.

킥의 규모 추정(117건)과 실측(211건)이 다른 건 흔하다. "기준선 스냅샷 → 0으로" 방식이면 숫자가 얼마든 구조가 흡수한다.

## 10. 이 프로세스가 맞지 않는 경우

되돌릴 수 없는 작업(데이터 삭제·결제·외부 발송)이 킥의 핵심이면 Auto-STOP만으로는 부족하다 — 실행 AI에게 그 명령 자체를 금지하고 사람이 직접 한다. 디자인 시안처럼 "정답이 없고 취향이 결정하는" 작업은 킥이 아니라 설계 파트너와의 토의로 먼저 확정하고, 확정본만 킥으로 넘긴다. 실시간 장애 대응은 킥 문서를 쓸 시간이 없으니 실행 AI와 직접 대화한다.
