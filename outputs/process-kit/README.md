# 킥 프로세스 킷 v1.0

**킥(Kick) 문서 하나로 AI 실행 파트너에게 일을 넘기고, 멈춰야 할 지점에서 스스로 멈추게 하고, 기계 검증 + 사람 검증을 거쳐 프로덕션까지 보내는 생산 라인** — 그 뼈대를 폴더 하나로 묶은 것이다.

이 폴더를 새 프로젝트 리포에 통째로 복사하고, 자리표시자(`{{...}}`)를 채우고, 아래 §3 순서대로 3일치 작업을 하면 같은 방식으로 일할 수 있다.

코드를 쓰지 않는 1인 기획자가 AI 둘(설계 파트너 + 실행 파트너)과 함께 쓰는 것을 전제로 만들었다. 사람이 하는 일은 세 가지뿐이다 — **결정, 눈으로 하는 검증, 자기 계정이 필요한 일**(API 키·로그인·결제).

---

## 1. 5분 요약

### 세 역할

| 역할 | 맡는 것 | 맡지 않는 것 |
|---|---|---|
| **의사결정자(사람)** | 최종 결정 · 눈으로 하는 검증(디자인·UX·콘텐츠) · 계정이 필요한 작업 · 우선순위 | 코드 작성, 명령어 암기, 로그 해석 |
| **설계 파트너(AI)** | 아이디어 토의 · 킥 문서 작성 · STOP 화면 해설과 선택지 추천 · 프로젝트 메모리 유지 | 리포에 직접 커밋(리포 밖에서 산다) |
| **실행 파트너(AI 코딩 에이전트)** | 킥 읽고 구현 · 테스트/가드/CI · PR·머지·배포 · 실측 보고 · 판단이 필요하면 STOP | 킥에 없는 스코프 확장, 추측을 사실처럼 보고, 사람 확인 없는 프로덕션 변경 |

> **설계 파트너의 메모리와 실행 파트너의 메모리는 서로 보이지 않는다.** 킥 문서에 "설계 파트너 메모리 X 참조"라고 쓰면 실행 파트너는 그 파일을 찾을 수 없다. 필요한 내용은 **킥 본문에 인라인으로** 넣는다.

### 한 바퀴

```
[사람 + 설계 파트너]  설계 토의 → 킥 문서 발행 → {{HANDOFF_DIR}}/ 에 저장
        ↓
[실행 파트너]          킥 읽고 착수 → Phase별 실행 → 판단 필요 지점에서 Auto-STOP
        ↓
[사람 ⇄ 설계 파트너]   STOP 화면 캡처 → 설계 파트너가 선택지 해설 → 결정 → 붙여넣기
        ↓
[실행 파트너]          PR 생성 → CI(테스트+가드) → 프리뷰 배포
        ↓
[사람]                 프리뷰/프로덕션에서 눈으로 검증 → 머지 승인
        ↓
[실행 파트너]          머지 → 배포 → 최종 보고(4블록 + "핸드오프와 달랐던 점") → 워크트리 정리
        ↓
[설계 파트너]          메모리 갱신 · 교훈 기록 · 다음 킥 대기열 정리
```

**이 프로세스의 본질은 "실행 AI에게 자유를 주되, 멈춰야 할 지점을 문서로 미리 정해두는 것"이다.** 킥 문서가 그 계약서다.

## 3. 새 프로젝트 온보딩 (Day 0 → Day 2)

### Day 0 — "킥 0": 안전장치만 깐다 (기능 없음)

이 날은 기능을 만들지 않는다. 다음 킥부터 재사용될 바닥을 깐다.

1. **`CLAUDE.md` 작성** — `CLAUDE.md.skeleton` 복사 → 실행 AI에게 "이 표를 리포 실측으로 채워라"고 시킨다. **"없는 것" 블록이 이 문서의 핵심이다** — 문서에 있다고 적힌 라이브러리가 실제로 없으면 실행 AI가 그 함정에 그대로 빠진다.
2. **테스트 기반선 green 확인** — 지금 상태에서 테스트가 전부 통과하는지. 킥은 여기에 "추가만" 한다.
3. **가드 1개 CI 편입** — `guard/` 를 `scripts/guard/` 로 복사, 규칙 1개라도 넣고 `guard/ci.example.yml` 을 `.github/workflows/` 에 설치.
4. **`predeploy-guard`** — `predeploy-guard.example.sh` 를 `scripts/` 로 복사, 배포 파이프라인 앞단(`package.json` 의 `predeploy` 스크립트, 배포 도구의 predeploy 훅, CI의 배포 스텝 직전)에 연결.
5. **Secrets 경로 정하기** — API 키는 서버 금고에만. 리포·클라이언트 코드·채팅에 절대 노출 금지.
6. **워크트리 관행** — 킥마다 `~/Projects/{{REPO}}-<킥코드>` 워크트리. 본 폴더는 항상 깨끗한 `{{MAIN_BRANCH}}`.
7. **PR 템플릿 설치** — `PR_TEMPLATE.md` → `.github/PULL_REQUEST_TEMPLATE.md`.
8. **킥 우편함 폴더 생성** — `{{HANDOFF_DIR}}/` (킥 문서를 여기 두고 실행 파트너가 읽는다).

### Day 1 — 작은 킥 1개

**"결과가 안 바뀌어야 하는" 리팩터링이 첫 킥으로 이상적이다.** 프로세스를 검증하면서 위험은 낮다. 이때 `harness/visual-diff/` 가 그대로 쓰인다.

### Day 2~ — 기능 킥

Auto-STOP이 2~3회 발동하는 정도의 크기. 하루 안에 프로덕션까지 가는 크기가 적당하다.

### 매 킥 후 (5분)

메모리 갱신 · `LESSONS.md` 한 줄 추가 · 다음 대기열 정리.

## 4. 자리표시자

킷 전체에서 쓰는 자리표시자다. 복사 직후 전부 치환한다 — 남아 있으면 실행 AI가 그 자리를 추측으로 채운다.

| 자리표시자 | 뜻 | 예 |
|---|---|---|
| `{{PROJECT}}` | 프로젝트/서비스 이름 | `Acme Board` |
| `{{REPO}}` | 리포 폴더 이름 | `acme-board` |
| `{{MAIN_BRANCH}}` | 배포 기준 브랜치 | `main` |
| `{{HANDOFF_DIR}}` | 킥 문서를 두는 폴더 | `outputs/handoffs-staging` |
| `{{PKG_MANAGER}}` | 패키지 매니저 (**실측**) | `npm` |
| `{{INSTALL_CMD}}` | 의존성 설치 | `npm ci` |
| `{{TEST_CMD}}` | 단위 테스트 | `npm test` |
| `{{BUILD_CMD}}` | 빌드 | `npm run build` |
| `{{GUARD_CMD}}` | 가드 실행 | `npm run check:rules` |
| `{{DEPLOY_CMD}}` | 배포 | `npm run deploy` |
| `{{NODE_VERSION}}` | CI Node 버전 | `20` |
| `{{KICK_CODE}}` | 킥 식별자 | `AUTH-1` |
| `{{DATE}}` | 날짜 | `2026-08-16` |

치환 후 남은 게 없는지 확인:

```bash
grep -rn "{{" . --include='*.md' --include='*.sh' --include='*.yml' --include='*.mjs' --include='*.json'
```

## 5. 셀프테스트

킷을 복사한 직후 한 번 돌린다. 임시 폴더에 픽스처를 만들어 가드·predeploy-guard가 실제로 잡고/막는지 확인한다. 의존성 없이 Node와 bash만 있으면 된다.

```bash
bash selftest.sh
```

CI 워크플로 문법 검증은 `actionlint` 가 PATH에 있으면 자동으로 쓰고, 없으면 YAML 파서(`yaml` 패키지)로 구조를 검증한다. 둘 다 없으면 그 단계만 SKIP으로 표시된다.

## 6. 이 프로세스가 맞지 않는 경우

**되돌릴 수 없는 작업**(데이터 삭제·결제·외부 발송)이 킥의 핵심이면 Auto-STOP만으로는 부족하다 — 실행 AI에게 그 명령 자체를 금지하고 사람이 직접 한다.

**정답이 없고 취향이 결정하는 작업**(디자인 시안 등)은 킥이 아니라 설계 파트너와의 토의로 먼저 확정하고, 확정본만 킥으로 넘긴다.

**실시간 장애 대응**은 킥 문서를 쓸 시간이 없으니 실행 AI와 직접 대화한다.
